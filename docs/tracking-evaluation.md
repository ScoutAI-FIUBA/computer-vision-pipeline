# Tracking evaluation workflow

Two local, free tools. Neither runs the pipeline or uses a GPU.

1. `scripts/tracking/prepare_eval_dataset.py` builds a review-ready dataset.
2. `scripts/tracking/evaluate_tracking.py` counts and compares human-confirmed review events.

## Review boundary

Automation never decides semantics. Scenario and difficulty are declared by a human on the command
line; every review field generated by the tools is `pending` until a human fills it in. Scenarios:
`crossing`, `partial_occlusion`, `full_occlusion`, `camera_motion`, `other`. Difficulty: `easy`, `medium`, `hard`.
Free-text observations go in `--note clip=text` / the `notes` field, not in the scenario label.

Boundary, explicitly:

- Tools may cut clips, attach existing runs, slice and re-index tracks, and count events a human already wrote.
- A **human** confirms every semantic label: whether a scenario is present, whether an ID switch / full loss /
  recovery happened, and whether a stable identity was involved. Attaching a run does not fill any review field.
- Attached baselines and printed commands are inputs for that review, never a verdict.

## 1. Prepare a dataset

```bash
python scripts/tracking/prepare_eval_dataset.py --output-dir eval/set01 \
  --source media/game027.mp4 \
  --window game027-crossing-01:120:420:crossing:hard \
  --window game027-occ-01:900:1300:partial_occlusion:medium \
  --note "game027-crossing-01=two players overlap near the right wing"
python scripts/tracking/prepare_eval_dataset.py --validate eval/set01/evaluation_manifest.json
```

`--window clip:start_frame:end_frame:scenario:difficulty[:source]` uses an exclusive end frame and must span at
least 5 seconds (shorter windows are rejected). With several sources, add the trailing source name or stem.
`--source-dir DIR` accepts a directory of videos. Aim for 3-5 clips; the tool warns when fewer are given.

Output layout (existing datasets and run directories are never overwritten):

```
evaluation_manifest.json     clip, source_video, path, scenario, difficulty, start/end_frame, duration_seconds,
                             fps, width, height, configuration{target_fps, frame_stride}, source_commit,
                             review_status=pending, plus encoding details, contact sheet, notes
tracking_review.jsonl        template: one `clip_review` record per clip, all fields "pending"
clips/<clip>.mp4             cut with cv2.VideoWriter (re-encoded, mp4v; recorded in `encoding`)
contact_sheets/<clip>.jpg    evenly spaced frames labelled with source frame numbers
runs/baseline/<clip>/annotated/, runs/candidate/<clip>/annotated/   separate, immutable run dirs
```

`target_fps` / `frame_stride` (defaults 15 / 10, change with `--target-fps` / `--frame-stride`) are recorded
configuration only: `modal_app_v2.py` has no such flags. Each clip also carries one **staged** Modal command per run
label (`suggested_run_commands`; `suggested_run_command` is the first label's), for example:

```
modal run modal_app_v2.py --staged --job-id eval-game027-crossing-01-baseline \
  --video-path /abs/eval/set01/clips/game027-crossing-01.mp4 --frame-start 0 --frame-end 299 \
  --segmented --segment-window 150 --segment-overlap 20 --possession-engine v5
```

- Commands are printed and **never executed** (`command_executed: false`); they cost GPU credits.
- Job ids are deterministic, `eval-<clip>-<label>` (`suggested_job_ids`); Modal only rejects empty ids and path
  separators, which clip names cannot contain.
- Modal's `--frame-end` is **inclusive** while the manifest's `end_frame` is exclusive, so the cut clip (N frames)
  uses `--frame-end N-1`; both are stored (`frame_count`, `modal_frame_end_inclusive`).

### Attach an existing run as the baseline (free, no GPU)

If a full-clip run already exists, attach its downloaded Modal job folder instead of re-running the window:

```bash
python scripts/tracking/prepare_eval_dataset.py --output-dir eval/set01 \
  --attach-run game027-crossing-01=outputs/game027-job/game027      # existing dataset
# or together with --source/--window to prepare and attach in one call
```

`--attach-run CLIP=JOB_DIR` (repeatable; `--attach-label` picks another run label, default `baseline`) expects
`job.json`, `tracking/current.json` and `tracking/generations/<gen>/{manifest.json,tracking-manifest.json,tracks.jsonl}`.
Masks are never read. It writes, into `runs/baseline/<clip>/`:

- `tracks.jsonl`: only rows with `start_frame <= frame_index < end_frame`, with `frame_index` re-indexed to the cut
  clip (`source frame - frame_offset`). Other fields, including source-relative `timestamp_seconds`, are unchanged.
- `run_metadata.json`: job id, tracking/stats generation ids, source job folder basename (no local paths), input
  fingerprint, pipeline config read from the job manifests (`unknown` when absent), `source_commit` (`unknown`:
  job folders do not record it), `tooling_commit` (this repo's HEAD), `frame_offset`, row counts and a `warning`.

Checks (nothing is written if any fails): the tracking generation is complete and not truncated, the window lies inside
its inclusive `frame_bounds`, the job's video frame count equals the source's, and the run dir has no
`tracks.jsonl` / `run_metadata.json` yet (never overwritten).

**Caveat:** the tracks come from tracking the whole source clip, so segment seams and identities differ from a run on
the cut window. It is a baseline *for the window*, not a window-specific rerun; a candidate run on the cut clip is not
perfectly like-for-like, so judge differences by the human-confirmed review events.

## 2. Review JSONL contract

One JSON object per line:

```json
{"clip":"game027-crossing-01","event":"id_switch","frame_index":318,"track_id":4000005,"stable_player_id":"player-008","notes":"Human-confirmed identity swap"}
```

- `event`: `id_switch`, `full_loss`, `successful_recovery` (aliases `switch`, `loss`, `track_loss`, `recovery`).
- `frame_index` (int >= 0) and `track_id` (int) optional; `track_id` is raw provenance only.
- `stable_player_id` optional non-empty string; canonical identity when known.
- Per occlusion episode record one outcome: `successful_recovery` OR `full_loss`.
- Records with `"record_type":"clip_review"` (the template) are not events; they are skipped in counts, but their
  clip counts as present and unfilled ones are reported as pending.
- Distinct raw track-ID counts are not a swap metric: a swap can keep the ID count unchanged.

Validate, listing every line-numbered error: `evaluate_tracking.py review.jsonl --validate`.

## 3. Evaluate and compare

```bash
python scripts/tracking/evaluate_tracking.py review.jsonl            # unchanged default report
python scripts/tracking/evaluate_tracking.py review.jsonl --per-clip --json
python scripts/tracking/evaluate_tracking.py --baseline baseline_review.jsonl --candidate candidate_review.jsonl
```

Comparison prints per-clip and total deltas (candidate - baseline; lower is better for `id_switch`/`full_loss`,
higher for `successful_recovery`). Totals cover clips on both sides only; clips on one side are flagged and excluded.
The tool reports numbers, it does not declare a winner.

## 4. Ground-truth annotation schema and MOTA/IDF1 fixtures

Not implemented as an evaluator. MOTA/IDF1 computation is a **follow-up**; this repo only ships the schema and
hand-computed sample fixtures in `tests/fixtures/tracking_gt/` (validated by `tests/test_tracking_gt_fixtures.py`).
Ground truth is JSONL, one header line then one object per annotated box:

```json
{"record_type":"header","annotation_version":1,"clip":"game027-crossing-01","fps":30.0,"width":1906,"height":1044,"start_frame":0,"num_frames":300}
{"record_type":"box","frame_index":318,"gt_id":"player-07","bbox":[x1,y1,x2,y2],"visibility":"visible","notes":""}
{"record_type":"ignore","frame_index":318,"bbox":[x1,y1,x2,y2],"reason":"crowd"}
```

- `frame_index`: clip-relative (0 <= i < `num_frames`), same indexing as the sliced `tracks.jsonl`. `start_frame` is the
  informational source offset of the clip. `gt_id`: stable ground-truth player id (aligns with `stable_player_id`),
  at most once per frame. `bbox`: pixel `[x1,y1,x2,y2]`.
- `visibility`: `visible`, `partial_occlusion`, `full_occlusion`. Boxes with `bbox: null` (fully occluded, no
  reliable box) are listed only for recovery metrics and are excluded from the MOTA/IDF1 counts below.
- `ignore` regions: non-players or areas excluded from false-positive counting.
- Predictions use the `tracks.jsonl` field names; the fixtures keep just `frame_index`, `raw_track_id` and
  `bbox_xyxy`. `bbox_xyxy` is **normalised** (0-1), so an evaluator multiplies by header `width`/`height`. For
  identity across segments use `stable_player_id` when present, else `raw_track_id`.
- Matching: IoU >= 0.5 (`iou_threshold` in `expected_metrics.json`), one prediction per GT box, per frame.

### Sample fixtures and hand-computed expectations

`gt.jsonl`: 10 frames, 2 players (`player-01`, `player-02`), 20 GT boxes, one ignore region. Predictions copy GT boxes
exactly, so IoU is 1 where a prediction exists; they differ only in track ids and presence.

Definitions: `MOTA = 1 - (FN + FP + IDSW) / G` with G = 20; `IDTP` = matches under the best one-to-one global
assignment of GT ids to track ids, `IDFP = P - IDTP`, `IDFN = G - IDTP` (P = predicted boxes),
`IDF1 = 2*IDTP / (2*IDTP + IDFP + IDFN)`.

| case | file | P | FN | FP | IDSW | MOTA | IDTP | IDF1 |
|---|---|---|---|---|---|---|---|---|
| perfect | `pred_perfect.jsonl` | 20 | 0 | 0 | 0 | 1.0 | 20 | 1.0 |
| id_switch | `pred_id_switch.jsonl` | 20 | 0 | 0 | 1 | 0.95 | 15 | 0.75 |
| missed_track | `pred_missed_track.jsonl` | 15 | 5 | 0 | 0 | 0.75 | 15 | 0.857143 |
| false_positive | `pred_false_positive.jsonl` | 23 | 0 | 3 | 0 | 0.85 | 20 | 0.930233 |

- perfect: track 1 = player-01, track 2 = player-02 on all frames. MOTA = 1 - 0/20 = 1. IDF1 = 40/40 = 1.
- id_switch: player-01 is track 1 on frames 0-4 and track 3 on frames 5-9. One switch (1 -> 3 at frame 5).
  MOTA = 1 - (0+0+1)/20 = 0.95. The global assignment keeps one of the two tracks for player-01 (5 frames, a tie that
  does not change the value) plus player-02 (10): IDTP = 15, IDFP = 20-15 = 5, IDFN = 20-15 = 5,
  IDF1 = 30/(30+5+5) = 0.75.
- missed_track: player-02 is never predicted from frame 5 (full loss, no recovery): FN = 5. MOTA = 1 - 5/20 = 0.75.
  IDTP = 15, IDFP = 0, IDFN = 5, IDF1 = 30/(30+0+5) = 6/7 = 0.857143.
- false_positive: track 9 on frames 3-5 over empty court: FP = 3. MOTA = 1 - 3/20 = 0.85. IDTP = 20, IDFP = 3,
  IDFN = 0, IDF1 = 40/(40+3+0) = 0.930233.

Intended follow-up outputs: MOTA, IDF1, ID switches, FP, FN, mostly tracked/lost, recovery after occlusion.
